# THE PARTS BIN: certified-image reuse registry (proposal, nothing built)

Status 2026-10-10: **proposal only.** No code, no inventory. Zero certified images exist today (the hatch image is at OVERLAY_PASSED, awaiting owner sign-off).

## What exists (inspected)
- The name "THE PARTS BIN" appears nowhere in the repo or in the project docs (full-text search of both). The owner says it was previously approved; if a spec exists outside what I can see, send it and this proposal gets reconciled to it.
- Image storage today is **per guide**: `src/data/guide-visuals/<guide>.ts` holds a `GuideVisualSet` (`guideId`, `application`, `steps[n] -> GuideStepVisual[]`). Files ship under `/guide-visuals/`.
- **Applicability metadata already exists** on every visual: `application` {year, make, model, engine, trim?} and `provenance` (status, sourceType, `generatedRaster` record, rawSha256/finalSha256, technical review, caption disclosure "Simplified illustration").
- **The gate already exists**: `visualRefusal(set, vis, guide, vehicle)` refuses unless the application matches the vehicle and every provenance check passes. `resolveStepVisuals` returns `[]`, never a substitute.
- The BMW pipeline layer already stamps each visual with `imageType` (LOCATE / IDENTIFY / DO), `elements` (hero/target ids) and the locked contract hash.

## Smallest compatible extension
No new storage and no new gate. One derived index plus one rule.

1. **Index, not a copy.** `parts-bin.index.json`, generated by a script from the existing guide-visual sets. One row per visual that is already `status: verified` and owner-approved: `{ visualId, sha256 (finalSha256), imageType, heroElements[], application, sourceGuide, sourceStep, contractSha256 }`. Nothing enters unless it is APPROVED in the factory and passes `visualRefusal` today. Rows are derived, so they cannot drift or be hand-edited in.
2. **Reuse rule.** A step in another guide may reference a bin row only if all hold: `applicationMatches` for the target vehicle; same `imageType`; the target step's required hero elements are a subset of the row's `heroElements`; the row has no open REVOKED flag; and the step's contract does not list an element the image omits. Otherwise the step generates its own image through the normal pipeline.
3. **Reuse is a reference, not a re-certification.** The reusing step stores `{ partsBinRef: sha256 }`; the resolver re-runs `visualRefusal` on the referenced visual at render time. If the source image is revoked, every reuse goes dark with it.
4. **Overlay stays per use.** The orange overlay is an editable SVG per step, so reuse needs its own overlay spec and overlay QA when the step number, label or callout differs. The image is shared; the guidance layer is not.
5. **Candidates never enter.** Anything not APPROVED (including OVERLAY_PASSED) is excluded by construction.

## Candidate reuse already visible in the 16 guides (needs certification first)
- `oil-drain-hatch-locate` (LOCATE) could serve any guide that only needs "where is the undertray hatch" for this car. Today that is guide 16 only.
- IDENTIFY images of shared hardware (drain plug) apply to guide 16 only. Cross-guide overlap is small for one vehicle; the registry pays off mostly across later vehicles with the same application.
